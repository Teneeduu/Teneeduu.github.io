# 算法思维反思日志

## 一、初始目标与思路（~150字）
我想做一个 Hole.io 风格的黑洞吞噬网页游戏：俯视角操控黑洞吞掉比它小的东西、越吃越大，电脑手机都能玩，有关卡、场景多样。一开始我故意没把需求写死，而是在提示词里加了一句"**你可以通过问我问题来完善游戏细节**"。因为我自己对视角、胜负条件、画风、技术栈都还没想清楚。这样设计，是想让模型先把我模糊的想法收敛成明确方案再动手，避免它凭空猜、我来回返工。事实证明这一句话很关键，它直接回了我四个选择题。

## 二、任务拆解与迭代过程（~250字）
我用"小步提示、逐轮验证"的方式推进。第一轮只要一个能跑的最小可玩版本；跑通后，我用极简提示"**1、2、3、4**"让它一次补齐手感、玩法、场景、音乐。最关键的一次 Prompt 修改，是把模糊的"让物体动起来"改成"**车要在路上开，不能乱跑**"——只多了"在路上""不能乱跑"这几个字，模型就把"随机游走"的算法换成了"沿车道行驶＋到边界掉头"，效果立刻对了。引入素材时，我也不再说"找个车模型"，而是直接把下载文件夹的**绝对路径**贴给它，它就自己挑文件、重命名、写进配置。每一轮我都要求它说明"改了什么／为什么"，方便我判断是否跑偏。

## 三、大模型的表现评估（~150字）
它最强的环节是"需求澄清"和"把一句话诉求翻译成具体实现"：一句"车在路上开"就能落地成路网车道逻辑。但在**大批量改动**时会出低级错误——有一轮我同时加了人物和两个建筑包，它把变量 `targetD` 写成 `targetH`，导致缩放值变成 NaN、模型全部消失；还漏拷了外链贴图导致没颜色。说明它在一次改太多东西时，容易前后命名不一致。

## 四、问题与修复策略（~200字）
最棘手的是"模型全消失"。我给的提示很具体："**显示说都用了模型，但都看不到了**"——这句精确的症状描述，帮它把排查方向从"加载失败"收敛到"渲染／缩放"，最终定位到 `targetD/targetH` 拼写不一致造成 NaN。修复用了三招：统一命名、贴图按包分子目录内嵌、蒙皮角色转静态网格。其中**最有效的是"精确描述现象＋要求它先说原因再改"**，这直接阻止了它盲目乱改。我还一度猜"城市模型是真凶"，它验证后纠正了我——把假设交给它证伪，也很有用。

## 五、最终总结（~200字）
我对"算法思维"的理解变了。以前觉得算法就是自己写循环、写判断；现在发现更关键的是"**把问题拆成可验证的小步、用精确语言约束状态**"。提示词里一个具体约束（"不能乱跑"）本质就是在定义算法的边界；一句精确的 bug 现象描述，等于给搜索空间剪枝。真正决定成败的，反而是工程纪律：命名一致、一次只引入一类资源、每步自检构建。我也体会到模型是个放大器——我的问题描述越清晰、约束越具体，它的产出就越准；我含糊，它就发挥、就跑偏。

## 六、作品的真实价值（~100字）
会继续用。它已经能在电脑和手机上真正玩起来，还部署到了 GitHub Pages（teneeduu.github.io/game/）。下一步想用 AI 建模补齐 3D 素材，把现在的 7 个关卡、道具、Boss 整体迁移到真 3D 版本。
